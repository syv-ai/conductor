    The graph record and compiling

    A graph reaches conductor as data. It is a small JSON record that says which nodes there are and what each of their inputs gets. Compiling checks that record against the nodes a registry has, works out how the graph will run, and lists whatever is wrong with it. The result is a Graph, which a host keeps and starts runs from.

    ← The overview

    A graph is plain data.

    An editor saves it, and make_graph writes the same record from Python. There's no @graph.

    Each input's entry is one kind.

    It is a constant, a graph input the caller gives, or the sources of the edges into it. So a record can't give one input a constant and an edge at once.

    Compiling reports what is wrong.

    A wrong graph still compiles, and its faults are in graph.problems. A hook that raises is one of them. A record of the wrong shape raises.

    The record

    A record lists the nodes and what each input gets Public

    The example graph on this page has the three nodes in the first sample.

    @registry.node("lines", title="Lines", description="Splits a text into lines.")
def lines(text: str) -> Series[str]:
    return text.split("\n")

@registry.node("shout", title="Shout", description="Shouts one line.")
def shout(line: str, mark: str = "!") -> str:
    return line.upper() + mark

@registry.node("join", title="Join", description="Joins texts with a plus.")
def join(texts: Series[str]) -> str:
    return "+".join(texts)

    This record is what make_graph writes for the three nodes, with the constant "?" for shout.mark. A GraphRecord has inputs, nodes and outputs. inputs declares each graph input once, by name, with its default if it has one: {"text": {}} here, or {"text": {"default": "a"}}. nodes maps each node's id to a NodeRecord, and outputs maps each graph output's name to the node output it is. The record has no order of its nodes. Where order matters, conductor takes them by id.

    A NodeRecord names the node it uses in node, its version (1 unless it says otherwise), its inputs, and display. That last one is the host's own data, like a position on a canvas. Conductor saves it and doesn't read it, and it's left out of the graph's fingerprint.

    Each input's entry, an InputEntry, is one of three kinds, and the one key it has says which (the full shape is in python -m conductor.about the-graph-record):

    • {"constant": "?"}: the same value on every call of every run.
    • {"graph_input": "text"}: the caller gives it when a run starts, as graph.run({"text": ...}). The name is one the record declares in inputs, with the default for when the caller gives none. Several inputs may name one graph input and share its value and its one default.
    • {"sources": [...]}: the outputs whose edges lead into this input. Several sources are alternatives, from different branches of one node.

    An input the record leaves out takes the node's own default. shout.mark would be "!".

    Places

    How a place in a graph is written Public

    Problems, events and saved runs all need to say where something is. base/place.py has one way to write each place, as a tuple for code and as text for people.

    lines.resultSource("lines", "result")

    It is an output of a node, written as its id, a dot and the output's name. This is where an edge or a graph output reads from.

    read.result.emailSource("read", "result", "email")

    It is one field of the value an output returns. A field's name may itself have dots, as in "Amount in USD.", but it can't start with one.

    loud/shout("loud", "shout")

    A node path names the node shout inside the subgraph node loud. Only the engine and its problems write one. A graph record never does.

    a name"shout", "text-split"

    Every node id, input, output, graph input and graph output in a record is a name. "a.b" and "loud/shout" aren't names, since places are written with those characters. The rule is in python -m conductor.about the-graph-record.

    make_graph is the one place that reads a place written as dotted text. A record stores a source as separate fields, {"node", "output", "field"}, so nothing parses it there. A graph output must be a whole output. One with a field is refused as invalid_record, and the one error in its ctx.errors is output_has_field.

    Reading a record

    Which faults raise and which become problems

    Graph.compile takes a GraphRecord, its JSON text, or that JSON as plain data.

    Why read_json exists

    Plain json.loads keeps only the last of two equal keys. In a record that would drop a node without a word. read_json parses with every key seen, and it's what Graph.compile uses for text. A host can call it on a request body too.

    The record

    Compiling

    What compiling does

    Graph.compile checks every node and edge against the definitions. It also works out, once for every run, where each input gets its value and which loops each node is in.

    The steps of the Compiler Internal

    A wrong shape in step 1 raises. Every fault found after it goes in graph.problems. The kinds of problem each step can find, each with an example, are in the problems page's section on compiling a graph (python -m conductor.about compiling-a-graph).

    1. Check the shape. RecordValidator turns the input into a GraphRecord, or raises.

    2. Put the nodes in order. Each node comes after the nodes its edges come from, with ties broken by id. Every node on a cycle gets a problem, and compiling goes on from the first of them by id.

    3. Find each node's definition in the registry, at the version the record names.

    4. Check the node's context, then each constant and default by its input's type. Then call compute_added_inputs, if the node has it, with those constants. The inputs it returns join the node's own.

    5. Give each input a compiled input, and check that each edge's type fits the input. The loops a node is in follow from its inputs.

    6. Call compute_outputs, if the node has it, with the constants and the types the edges carry. What it returns replaces the outputs the node declares.

    7. Check the graph outputs. Each must name an output of a node the graph has.

    A subgraph used as a node is compiled on its own record. Its problems become this graph's problems, each loc starting with the subgraph node's id. Subgraphs have a page of their own.

    A node is left out of the compiled nodes when its definition isn't found, its hook fails or can't be called, or it is a subgraph with problems of its own. Every other node is kept, even with a problem on one of its inputs, so an editor can still draw it.

    An edge from a node that didn't compile gets no second problem. The input it leads into has no value, and the first problem says why.

    Where each input gets its value

    Inside, each input of a compiled node is one of the frozen dataclasses in graph/input.py. Each says where the value comes from. You see them in describe(), as the mode of the input's InputSource. Each card names the dataclass and the modes it shows as.

    ConstantInputmode: constant

    It is the record's constant, checked by the input's type when compiling, or else the node's own default, as for shout.mark.

    GraphInputmode: graph_input

    The caller gives it, by the graph input's name, as for lines.text.

    EdgeInputmode: item, one_value or outer_value

    It gets one value per call through its edges. shout.line gets one item of lines.result per call. One value is never a list of one: a Series input wired to one value per call is type_mismatch_series_given_one_value.

    CollectingInputmode: collected

    It is a Series input that gets one value per item of a loop, as a list, as join.texts does.

    MissingInputmode: missing

    It has no value, because the graph has a problem there. The node is kept, so an editor can draw this input as unset.

    graph = Graph.compile(record, registry)   # the record above
print(graph)
print(list(graph.inputs), {name: port.type for name, port in graph.outputs.items()})
for node_id, n in graph.describe().nodes.items():
    print(node_id, n.per_item_of,
          [(i.port.name, i.source.mode, i.source.series) for i in n.inputs])
print(graph.run({"text": "a\nb"}).outputs)

    Edges

    Whether an edge's types fit Public

    Compiling checks whether a value of an edge's output type can go to its input's type, from the declared types alone. An edge that doesn't fit is the problem type_mismatch, before anything runs. A few common mistakes have a kind of their own, whose message says the fix.

    @registry.node("count", title="Count", description="Counts the characters of a text.")
def count(text: str) -> int:
    return len(text)

T = TypeVar("T")

class Person(TypedDict):
    name: str
    email: str

class Named(TypedDict):
    name: str

@node("flag", title="Flag", description="Says yes.")
def flag(text: str) -> bool: ...

@node("numbers", title="Numbers", description="Gives some numbers.")
def numbers() -> list[int]: ...

@node("person", title="Person", description="Gives a person.")
def person() -> Person: ...

@node("half", title="Half", description="Halves a number.")
def half(n: float) -> float: ...

@node("anything", title="Anything", description="Takes any value.")
def anything(value: Any) -> Any: ...

@node("first", title="First", description="Gives the first item of a list.")
def first(items: list[T]) -> T: ...

@node("joinlist", title="Join list", description="Joins a list of texts.")
def joinlist(texts: list[str]) -> str: ...

@node("greet", title="Greet", description="Greets a person by name.")
def greet(who: Named) -> str: ...

    "Series[str] -> list[str]": (lines, joinlist),
    "Person -> Named": (person, greet),
}

for label, found in problems.items():
    print(label, [p.type for p in found])
print(problems["bool -> float"][0].msg)

'flag.result' gives bool, but 'half.n' takes float. Wire an output that gives float, or convert the value in a node in between.
'lines.result' gives Series[str], but 'joinlist.texts' takes list[str]. To take every item as one list, declare the input Series[str] in place of list[str].

    An empty list means the edge fits. An int is widened to a float, but a yes or no isn't a number. Any fits either way. list[int] binds T to int for that node, and a TypedDict fits by its keys. A Series into a list has a kind of its own, whose message says the fix. The rules are in python -m conductor.about types, under "What lands where".

    An input can ask for more than its source promises, such as a limit on the input. Then the value is checked when it arrives at run time. That check is on the running and streaming page. An edge whose source already satisfies its input isn't checked at all.

    From Python

    make_graph writes the same record Public

    make_graph(*nodes, edges=None, constants={}, defaults={}, inputs={}, outputs={}) writes a GraphRecord. It follows scikit-learn's make_pipeline. With no edges, the nodes form a chain. It declares the graph's inputs and outputs, and compiles nothing.

    The sample prints each record with dumps, a small JSON formatter that isn't part of conductor. Every JSON block on these pages is laid out this way: two spaces of indent, one key per line, and a list on one line when it fits.

    record = make_graph(lines, shout, join)
print(dumps(json.loads(record.model_dump_json())))
print(Graph.compile(record, registry).run({"text": "a\nb"}).outputs)

    A chain. Between two nodes, the edge goes from the one output of the first into the one required input of the second that constants=, defaults= and inputs= don't name. A subgraph node is chained by the graph inputs and outputs its record declares, so make_graph(lines, loud, join) chains through the subgraph loud. A node whose ports a hook works out takes edges=.

    Graph inputs and outputs. Each required input that gets nothing becomes a graph input under its own name (text), unless it takes only a constant. So does each key of defaults. Each output of a node that no edge leaves becomes a graph output (result). inputs= and outputs= name others. An optional input that inputs= names keeps its own default, so m above defaults to "!" and isn't required. A key of defaults gives its own. A node with a compute_outputs hook that no edge leaves needs outputs= to name what the graph returns from it. Without that, make_graph raises hook_outputs_not_named.

    Ids. A definition used twice gets shout-1 and shout-2, so no node keeps the bare id shout for another to take over.

    What it raises. make_graph raises one InvalidCallError with every fault it can see while writing. In the last call, "lines" isn't "node.name", so it is invalid_place and that edge isn't written. With an edge left out, make_graph makes no automatic graph inputs or outputs, so a name clash that would only follow from the gap isn't listed.

    What it leaves to compiling. It writes some faults as given: an input a node doesn't have, a value its type refuses, types that don't fit. Graph.compile(...).problems reports them.

    Hooks

    Compiling works out the inputs and outputs a graph decides Public

    A node can have a compute_outputs or compute_added_inputs hook. Compiling calls it with the constant, or else the declared default, of each input it names. For a parameter annotated type, compute_outputs gets the type the edge into that input carries. A hook that raises an exception is a problem on its node, not an exception from Graph.compile. The hooks themselves are on the page about nodes.

    calls = []

def branch_outputs(names: str, value: type) -> dict[str, Any]:
    calls.append((names, value))
    if not names:
        raise ValueError("names is empty")
    return {name: (value, SKIPPED) for name in names.split(",")}

@registry.node("route", title="Route", description="Gives the value to the output it names.",
               compute_outputs=branch_outputs)
def route(value: Any, names: str, chosen: str) -> dict[str, Any]:
    return {chosen: value}

graph = Graph.compile(make_graph(count, route,
    edges=[("count.result", "route.value")], constants={"route.names": "small,big"},
    outputs={"small": "route.small", "big": "route.big"}), registry)
print(calls)
print([(f.name, f.type, f.required) for f in graph.describe().nodes["route"].outputs])
print(graph.run({"text": "hello", "chosen": "big"}).outputs)

    Versions

    registry.upgrade moves one node of a saved record Public

    A record names each node's version, and compiling uses that version. To move it, a host calls registry.upgrade(record, node_id, *, to=None), which runs each newer version's Upgrade in turn and returns a new record. It compiles nothing.

    @node("shout", title="Shout", description="Shouts one text.")
def shout_v1(text: str, mark: str = "!") -> str:
    return text.upper() + mark

@node("shout", title="Shout", description="Shouts one line.", replaces=shout_v1,
      upgrade=Upgrade(renamed_inputs={"text": "line"}))
def shout_v2(line: str, mark: str = "!") -> str:
    return line.upper() + mark

versions = NodeRegistry()   # a registry with shout at version 2
versions.add(shout_v2)

saved = GraphRecord.model_validate({"inputs": {"text": {}}, "nodes": {"s": {"node": "shout", "inputs": {
    "text": {"graph_input": "text"}, "mark": {"constant": "?"}}}},
    "outputs": {"result": {"node": "s", "output": "result"}}})
graph = Graph.compile(saved, versions)
print(graph.problems == [], graph.run({"text": "hi"}).outputs)
moved = versions.upgrade(saved, "s")
print(dumps(json.loads(moved.model_dump_json())))
print(Graph.compile(moved, versions).run({"text": "hi"}).outputs)
print(versions.upgrade(moved, "s") is moved)

    • A rewrite gets the node's constants as one dict, and every key it returns becomes a constant. A graph input's default belongs to the whole graph, so no rewrite changes it.
