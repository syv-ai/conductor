    Series and tables

    A node's types say how many values it deals with. str is one value. Series[str] is many values of one type, and each value in it is an item. Table[R] is a whole table, passed along an edge as one value. From those types alone, conductor works out whether a node is called once or once per item.

    Every sample output and widget state on this page is what the code it shows prints.

    ← The overview

    Series[T] is many values.

    Wired to an input that takes one T, it starts a loop. That node is called once per item. The node itself gets a plain list, and a type checker sees one too.

    Table[R] is one value.

    A TypedDict R names its columns, and a bare Table takes any columns. Inside the node it is a polars.DataFrame. It never starts a loop.

    list[T] is one value too.

    A list given to an input of one str is refused. It does not start a loop.

    Publicwhat you import, write or read back

    Internalhow conductor does it inside; you never import it, and it can change in any release

    A loop

    A loop calls a node once per item, then once for all of them Public

    lines returns a Series[str]. shout takes one str, so it is called once per line. join takes a Series[str], so it collects the loop. It waits until every call of shout has an outcome. Then it is called once with all of them, in item order. Change the number of lines, or what join takes, and see what the run did.

    Progress

    How many calls shout will have depends on how many lines lines returns. The first line the sample prints is the count of shout before lines has returned, and the last is the count after it returned three lines.

    Item indexes

    How a call is named Public

    A node inside a loop can return a Series too. Here each document has lines of its own, so the loop over the lines sits inside the loop over the documents. A call's item indexes are one index per loop it is inside, outermost first. Tap a call to see how it is named.

    Three ways to say which call

    • Item indexes are the indexes alone: (0, 1) is line 1 of document 0. A node inside no loop has ().
    • A loc puts each index right after the id of the node inside that loop, in the graph where the loop is: ("approve", 0, 1). A problem names a call by its loc, and so does run.none_input_calls.
    • The text joins node ids with / and puts @ before each index: approve@0@1. A waiting call’s id is that text, then ~ and a fingerprint of the call: the node's code, the call's inputs and its item in each loop.

    Inside a subgraph, the index goes after the subgraph node when the loop is in the outer graph. The inner node shout of a subgraph node loud that runs per line is ("loud", 1, "shout"), written loud@1/shout. That is why no node id or name may contain ., /, @ or ~.

    Where an input's value comes from

    Compiling decides where each input gets its value

    The type decides how many values an input takes Public

    One value is never a list of one. An edge that gives each call one value, wired to a Series input, is the compile problem type_mismatch_series_given_one_value at that input, and the graph doesn't run. A list the caller gives to an input of one str is refused with invalid_input_list_for_one_value.

    The other way round, a Series output wired to an input that takes a plain list is refused too. The edge gives that input one item per call, and one item isn't a list. Compiling reports type_mismatch_series_into_list, and its message says the fix: declare the input Series[T], which takes every item as one list.

    Two series that are not one inside the other never pair up item by item. Compiling reports series_not_nested at the node where they meet. To fix it, put one inside the other, or give one of them whole to a Series input.

    The rules are in python -m conductor.about one-or-many, and each code on the problems page.

    Which items are left out

    An item with no value is left out of a Series[X] input. When a node has two such inputs collected from one loop, an item with no value in either is dropped from both, so names[i] and emails[i] are still the same item. Series[X | None] keeps the item's place as None.

    What collecting does when no item could have a value, as when every call is downstream of a branch that wasn’t chosen, is in python -m conductor.about one-or-many, under "What collecting leaves out".

    What a node returns for a Series

    A node may return a frame for a Series of rows

    What a node returns for a Series output is checked by the output's type. For Series[R], with R a TypedDict, or for Series[dict], Series[dict[str, Any]] or Series[Any], a node may return a polars.DataFrame instead of a list.

    What a Series is read from Public

    From Python, a node may return a tuple, a range or a polars.Series, such as a column of a table. Each is read as a list of its values. A set is refused, because its order can change from one process to the next. The rule is in python -m conductor.about types.

    A type checker sees Series[T] as list[T], so it wants a list returned. The engine accepts the others.

    RETURNS = {"list": ["a", "b"], "tuple": ("a", "b"), "range": range(2), "polars.Series": pl.Series(["a", "b"]), "set": {"a", "b"}}

    A run keeps a Series as a list or as a frame Internal

    A list becomes a SeriesItems. A frame is kept as it is, as SeriesRows. Both have the same methods, so the code that reads a stored Series never checks which one it has.

    Why keep the frame

    An edge that names a field reads one column of the frame, and a column that no edge reads stays in the frame until the run is saved.

    The frame is checked as a Table[Contact] when the node returns it, so it has exactly Contact's columns. The phone column is gone before anything reads it. A saved run writes SeriesRows as a table's JSON, and SeriesItems as a JSON array.

    A SKIPPED item has no JSON form, so for_saving() writes it as None and lists its index beside the Series. A frame has no SKIPPED row.

    A whole table as one value

    Every form of a table becomes one frame

    A table can arrive as a polars.DataFrame, as a list of rows with one dict per row, or as the JSON conductor writes for a table. Whatever the form, a Table[R] reaches the node as a frame with exactly the columns R names, each of its declared type. That holds for a caller's value, a constant, a person’s answer, collected rows and a node's own return. A constant is JSON, so it is never a frame. The rules are in python -m conductor.about types and, for which tables fit, python -m conductor.about one-or-many.

    A table never starts a loop Public

    A table is passed whole. A column of it is no source. An edge to contacts.result.email from a Table output is unknown_output_field_of_whole_table_or_list. To run per row, a node returns Series[R]. Split in syv-conductor-nodes does that for any table or list.

    The other way, a Table[R] input wired to rows inside a loop collects them into one table, the way a Series input collects items. What a row type may declare is in python -m conductor.about one-or-many, under "A table is one value".

    The item limit

    max_items stops a run before it spends Public

    graph.run(max_items=n) limits how many items any one series a loop runs over may have. Over the limit, the run stops with the problem item_limit. The limit is on each series alone, never on all their items together.

    text
    max_items 3
    run.status
    run.cause.type, .loc and .ctx
    calls of shout, and the outputs

    The graph is docs -> lines -> shout. docs splits on |, lines on commas, and shout runs per line. No node in it uses threads. In the stopped runs, shout was not called at all.

    Only what a loop runs over counts

    A series that is only collected or passed whole costs no calls, so it is not counted. A Series of rows kept as a table counts its rows.

    The run is stopped, not failed. run.with_max_items(n) is the same run under a new limit, and resume() goes on from there without calling again what was already called. The limit belongs to the run, so resume() and stream() don't take it.

    max_items must be a whole number of at least 1; anything else is invalid_limit. The rules of the limit are in python -m conductor.about one-or-many, under "The item limit".

    Why it's built this way

    The choices this part makes

    Why the type decides one or many, why a table never starts a loop, why two series never pair up by themselves, why the item limit stops a run without failing it, what collecting does when no item could have a value, and why a Series of rows keeps its table are in the design guide, under "One or many", "None and values from outside a loop" and "Saved runs, checkpoints and events". The others are here.

    A Series is a plain list to the node and to a type checker.Public

    The author writes no new collection type and calls nothing special. Series exists so pydantic finds its schema, and under TYPE_CHECKING it is list[T].

    Cost: the engine accepts a returned polars.Series, but a type checker wants series.to_list().

    A table is kept the way a saved run reads it back.Public

    Each column is converted to the type it comes back as from JSON, or refused. So a run behaves the same before and after it is saved and resumed in another process, save for a column with no value at all, whose type may not come back.

    Cost: some frames are refused that polars itself holds fine, such as a Datetime in Copenhagen time. The node converts it first.

    Progress is worked out from the outcomes.Public

    run.progress is read from the outcomes each time, so there is no counter to keep in step, and a run read back from JSON has the same progress.
