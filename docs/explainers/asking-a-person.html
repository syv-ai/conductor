    Asking a person

    Some nodes can't finish on their own. They need a person to approve something, pick an option or type a reason. Such a node raises Ask. Its call stops and waits, the rest of the run goes on, and the person's answer becomes the node's outputs, as if the function had returned them.

    A node raises Ask.

    Its @node says asks=True. The return type says what kind of answer it takes.

    The call waits while the rest runs on.

    The call that asked, and every call downstream of it, wait. With nothing else wrong, the run ends waiting.

    The answer is the outputs.

    run.with_answers checks it and stores it as the call's outputs. The next resume() goes on from there. When a person says no, the host calls run.with_decline. That ends the run declined, for good. run.again() starts a new run that asks again.

    What is asked

    The return type is the question

    The answer fills the node's outputs, so each output is one question. The Ask adds only what is known as the node runs.

    The node, and an answer to it

    The question, as run.waiting writes it

    Printed from model_dump(mode="json") in the series' JSON layout (two-space indent, a short list on one line), with title, description, widget, type_variables, loops and constant_only left out to save room. A node with several questions prints them as a list. run_alone(node, ...) runs a graph of that one node.

    Answering

    An answer is checked before anything is stored Public

    run.with_answers(waiting, value) answers one call, and run.with_answers({id: value, ...}) answers several. Each returns a new run, and nothing runs until resume(). A node with one question takes a plain value. A node with several takes a mapping by question name.

    Try an answer

    @dataclass(frozen=True)
class Closing:
    reason: str
    hours: float = 1.0
    comment: str | None = None
    escalate_to: str = SKIPPED

@node("close", title="Close", description="...", asks=True)
def close(ticket: str) -> Closing:
    raise Ask(f"Close {ticket}",
              choices={"escalate_to": ["ida", "bo"]})

closing = run_alone(close, ticket="T-7")

    A decline ends the run for good, and again() asks again

    A decline is not an answer: a person said no. The run is declined, with answer_declined as its cause, and nothing waits any more. Every call made before keeps its outcome. To reject one item and let the run go on, answer it instead.

    run.again() starts a new run that reuses what this one ran and calls the declined node again, so it asks again, under the same id. A reason that isn't text is refused, and the run is left as it was. The rules are under "Declining" in python -m conductor.about asking-a-person.

    The waiting id

    An id names the call and the question Public

    A host stores the id and sends it back with the answer, maybe days later. The id below is the inner approve of a subgraph check, for the second line of the second document. Tap a part.

    A waiting call is a few bytes of JSON

    A call that asked is saved with its prompt, the choices and defaults the Ask set, and the call's fingerprint, taken when the call was made. It has no outputs yet. Once a person answers or declines, the run keeps the question for run.asked.

    run.asked lists every call a person answered or declined: the question as they were shown it, and their reply. A host that keeps runs as a record reads it, from a run read back too. The call's arguments aren't saved with it, only their fingerprint. run.waiting works the arguments out again from the outcomes upstream that the call read, and those don't change while it waits. The id is hashed from the saved fingerprint and the node's code fingerprint now. So the question a loaded run shows is the one first asked, id included, while the node's code is the same.

    Running again keeps the answers

    A node that may ask reuses its earlier outcomes in item order. Answer False about "a long line", then run again with a line put in front. Nothing is asked.

    before = graph.run({"text": "a long line\nok"})
before = before.with_answers(before.waiting[0], False).resume()
after = before.again({"text": "new\na long line\nok"})
print(after.status, after.results["approve"], after.waiting)
    complete {'result': [True, False, True]} []

    What status a run has after an answer is under "The status" in python -m conductor.about running, and what a later run reuses is in python -m conductor.about running-again.

    The problems

    A node that asks wrongly ends its run with a problem as the cause, and an answer or a decline the run can't take is refused with one. Every kind, with its ctx and an example, is on the problems page (python -m conductor.about problems). The samples above show invalid_answer, invalid_ask, invalid_decline_reason, not_waiting, answer_stale and answer_given_twice as they print.

    Why it's built this way

    The design choices Public

    Why the return type is the answer's type, why a node says asks=True, why the answer becomes the outputs, why Ask is a BaseException, and what the waiting id guards: each is argued, with what it costs, under "Asking a person" in the design guide. The full rules are in python -m conductor.about asking-a-person.

    A waiting call shows and fingerprints what it was given.

    A person is shown the call's inputs, and the waiting id hashes them, so an answer is tied to what was asked.

    Cost: a node that asks needs inputs with a JSON form, since they are shown and hashed. Without one the call fails as question_unwritable.
