    Asking a person

    Some nodes can't finish on their own. They need a person to approve something, pick an option or type a reason. Such a node raises Ask. Its call stops and waits, the rest of the run goes on, and the person's answer becomes the node's outputs, as if the function had returned them.

    A node raises Ask.

    Its @node says asks=True. The return type says what kind of answer it takes.

    The call waits while the rest runs on.

    The call that asked, and every call downstream of it, wait. With nothing else wrong, the run ends waiting.

    The answer is the outputs.

    run.with_answers checks it and stores it as the call's outputs. The next resume() goes on from there. When a person says no, the host calls run.with_decline. That ends the run declined, for good. run.again() starts a new run that asks again.

    Publicwhat you import, write or read back

    Internalhow conductor does it inside; you never import it, and it can change in any release

    Answering
    
    
    An answer is checked before anything is stored Public
    
    
    run.with_answers(waiting, value) answers one call, and run.with_answers({id: value, ...}) answers several. Each returns a new run, and nothing runs until resume(). A node with one question takes a plain value. A node with several takes a mapping by question name.
    
  
    

  
    
    
    
      
    
    
    
    
      
    Try an answer
    
      
    @dataclass(frozen=True)
class Closing:
    reason: str
    hours: float = 1.0
    comment: str | None = None
    escalate_to: str = SKIPPED

@node("close", title="Close", description="...", asks=True)
def close(ticket: str) -> Closing:
    raise Ask(f"Close {ticket}",
              choices={"escalate_to": ["ida", "bo"]})
    
      
    
      
    
    
    
  
    

  
    
    
    
      
    An answer is read as its JSON text would be
    
      
    For -> bool, True is taken and "yes", 1 and "true" are each refused with Input should be a valid boolean. A date takes its ISO text, such as "2026-11-20".
    
    
    
    
    
      
    Every fault is reported at once, and nothing is answered
    
      
    One InvalidCallError carries a problem per fault, across every call in the mapping. Each invalid_answer from run.with_answers has ctx.waiting_id, ctx.reason (the first error's message) and ctx.errors (pydantic's codes, such as bool_type, missing or not_a_choice, each with a loc inside the question's value), and ctx.question when the fault is about one question of several. They come in the order of the questions, then the names that aren't questions, then the answer as a whole. One call answered twice in one mapping, under its whole id and its short id, is answer_given_twice. No message quotes an answer's value.
    
    
    
    
    
      
    A node's branches take at most one answer
    
      
    Outputs whose default is SKIPPED are branches, and a call gives a value to at most one of them. A person is held to the same rule as a returning node. Answering {"keep": "yes"} and resuming gives {'drop': None, 'keep': 'yes'} as the outputs. Answering neither skips both. Answering both is refused: 'keep' and 'drop' both have a value, but they default to SKIPPED, so they are branches of one node.
    
    
    
    
    
      
    An Ask's defaults fill one branch at most
    
      
    An Ask may propose a default for one branch, such as default={"keep": "yes"}. An answer that leaves out both branches then gives {'drop': None, 'keep': 'yes'}. Defaults for two branches fail the node with invalid_ask: the default is wrong ('keep' and 'drop' both have a value, but they default to SKIPPED, so they are branches of one node). The defaults fill in one answer, and one answer gives a value to one branch at most.
    
    
    
    
    
      
    A pick of several picks each once
    
      
    An answer to a Series output whose items have choices may not pick one twice: a choice is picked twice. A person's answer, and an Ask's default, are held to that. A node may return a Series that has a value twice.
    
    
    
    
    
      
    The Ask is checked when it is raised
    
      
    Conductor checks the choices and default against the outputs before the call waits. Ask("Who?", choices=[1, 2]) on -> str fails the node: the choices for 'result' are wrong (Input should be a valid string). So does an empty list of choices, one given twice, a name that isn't an output, and a default a person couldn't give. Every fault is in ctx.errors, each loc starting with choices or default, then the output's name. A key that is no output is written "[key]" there, never quoted.

#   ctx: {'waiting_id': 'approve@1~23c82614', 'errors': [{'type': 'string_type', 'loc': [], 'msg': 'Input should be a valid string'}]}
run.status
# 'waiting'
    
    
    
    
    
      
    A decline ends the run for good, and again() asks again
    
      
    A decline is not an answer: a person said no. The run is declined, with answer_declined as its cause. Every call made before keeps its outcome, so run.results shows what ran. To reject one item and let the run go on, answer it instead.
    
      
    Nothing waits any more, so with_answers and with_decline refuse every id as not_waiting, and resume() calls no node. A saved run reads back the same. run.again() or run.with_inputs() starts a new run that reuses what this one ran and calls the declined node again, so it asks again, under the same id while its inputs and code are the same. The reason is checked as its JSON text would be: text, or None.

    Load, answer, resume

    The call's arguments aren't saved with it, only their fingerprint. run.waiting works the arguments out again from the outcomes upstream that the call read, and those don't change while it waits. The id is hashed from the saved fingerprint and the node's code fingerprint now. So the question a loaded run shows is the one first asked, id included, while the node's code is the same.
    
    
    
  
    

  
    
    
    
      
    The status after an answer
    
      
    Once every waiting call is answered, a run is ready if calls are left to make and complete if none is. A failed or stopped run stays that way until a resume() tries again, since the failed call or the long series is still there. A cancelled or timed_out belonged to that one resume, so an answer drops it. A declined run takes no answer at all.
    
    
    
    
    
      
    Running again keeps the answers
    
      
    A node that may ask reuses its earlier outcomes in item order. Answer False about "a long line", then run again with a line put in front: again({"text": "new\na long line\nok"}) is complete with [True, False, True], and nothing is asked.
    
    
    
  
    

    


    



    
  
    
    
    What a host is shown
    
    
    A host sees a question before, during and after a run Public
    
  
    
  
    
    
    
      
    Before a run, registry.describe() says which nodes may ask
    
      
    Each node in registry.describe() says whether it may ask, and so does a definition's own describe(). For a compiled graph, graph.asks says whether any node of it may ask. A subgraph asks when a node inside it does, however deep. From the id sample: {'lines': False, 'approve': True, 'docs': False, 'check': True}.
    
    
    
    
    
      
    During a stream, the node_waiting event says a call waits
    
      
    A stream sends NodeWaiting as soon as the outcome is written, with the Waiting inside. For a graph of the confirm node above, given the ticket "T1", it printed run_start, node_start, node_waiting confirm~18ccd40e, run_end waiting. The node that asked gets no node_complete in that stream.
    
    
    
    
    
      
    After a run, run.waiting lists every waiting call
    
      
    Each is a Waiting, in node order and then item order. A Waiting has id, loc, prompt, questions and inputs. It is a pydantic model, so a host sends it with model_dump_json() and draws it with no graph loaded. A call inside a subgraph is listed where its subgraph node is.
    
    
    
  
    
  
    The problems
    
  
    
    
    
      
    typewhenwhere it shows
    
      
        
    ask_not_declaredA node raised Ask without asks=True, from a function it calls or in another way @node can't see in its source. (A raise Ask(...) in the function's own body is refused by @node already, as ask_not_declared_in_source.) The message: The node asked a person, but its @node doesn't say it may. Add asks=True to its @node.the run's cause. The run is failed.
    
        
    invalid_askThe Ask's choices or default don't fit the outputs. ctx.reason says which part first, and ctx.errors has every fault.the run's cause
    
        
    question_unwritableThe call's inputs have no JSON form, so a person couldn't be shown them. ctx.input names the input, and ctx.error is the class of the exception writing it raised.the run's cause
    
        
    answer_declinedA host declined the question with run.with_decline. ctx.reason is the host's reason, left out when it gave none.the run's cause. The run is declined, for good.
    
        
    invalid_answerAn answer its question refuses. ctx.reason is the first error's message, and ctx.errors has every fault. The run is left as it was.raised by run.with_answers
    
        
    answer_given_twiceOne call answered twice in one with_answers, under its whole id and its id without the ~ part. ctx.waiting_id is the second. Neither answer is taken.raised by run.with_answers
    
        
    invalid_decline_reasonA decline's reason that isn't text JSON can write. ctx.errors says why without the reason (string_type, no_json_form). The run is left as it was.raised by run.with_decline
    
        
    not_waitingThe id names no waiting call. ctx.status is the run's status, and ctx.moved_to is there when the question now waits on another call.raised by run.with_answers or run.with_decline
    
        
    answer_staleThe call still waits but now asks another question. ctx.current is the question waiting there now, and ctx.moved_to is there when the old question now waits on another call.raised by run.with_answers or run.with_decline

    Why it's built this way
    
    
    Eight design choices Public
    
    
    The longer case is in docs/design.md, under "Asking a person". The full rules are in python -m conductor.about asking-a-person.
    
  
    
  
    
    
    
      
    The return type is the answer's type.
    
      
    The node already declares what its outputs are, and the answer fills them. An AskBool class or a type= argument would say it a second time.
    
    
    
    
    
      
    A node that asks says so with asks=True.
    
      
    A host needs to know, before a run, whether a call may wait for a person. @node refuses a function whose own body raises Ask without it (ask_not_declared_in_source), and any other Ask without it fails as ask_not_declared, so asks in registry.describe() can be trusted.
    
      
    Cost: the signature alone doesn't say everything the node does.
    
    
    
    
    
      
    The answer becomes the outputs. A node that needs it reads an edge.
    
      
    "Approve, then pay" is two nodes: approval(invoice) -> bool asks, and pay(invoice, ok: bool) reads approval.result. The answer then has one shape and one place where it is kept, saved and reused.
    
      
    Cost: the question shows on approval, not on the step a person thinks of. A host can wrap the two in a subgraph to offer them as one node.
    
    
    
    
    
      
    A question is the output's own description.
    
      
    A question is the FieldDescription that describe() gives the output, with the Ask's choices and default. So a host draws a question with the code that draws an input, and how it looks comes from the type's Param. Ask takes no widget=.
    
    
    
    
    
      
    Ask is a BaseException.
    
      
    So a node's except Exception doesn't swallow the pause and carry on with a wrong value. An except BaseException or a bare except: still would.
    
    
    
    
    
      
    An answer is read strictly, and refused whole.
    
      
    Reading from the JSON form makes an answer from Python and one over HTTP the same. Reporting every fault in one error lets a form mark all its fields at once, and nothing half-answered is left in the run.
    
    
    
    
    
      
    The id carries a fingerprint of the question.
    
      
    It hashes the call's fingerprint, the one reuse matches calls by, and the node's code fingerprint now. The call's fingerprint is taken once, when the call is made, from the code fingerprint, the call's inputs and the call's item in every loop it is inside, and the run keeps it with the call. The code fingerprint covers the node's code, version, input and output types, which outputs are branches, its loops and asks. Another input, new code or a new version gives another id, so a deploy that changes the node's code changes the id of a call already waiting. An answer meant for a question that has changed since is refused rather than given to the new one. The prompt, choices and default aren't in it.
    
      
    Cost: an id without its ~ part answers whatever waits at that call. That short form is for a person typing about the run in front of them. A host stores the full id.
    
    
    
    
    
      
    A waiting call shows and fingerprints what it was given.
    
      
    A person is shown the call's inputs, and the waiting id hashes them, so an answer is tied to what was asked.
    
      
    Cost: a node that asks needs inputs with a JSON form, since they are shown and hashed. Without one the call fails as question_unwritable.
