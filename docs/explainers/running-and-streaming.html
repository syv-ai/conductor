    Running and streaming

    A compiled graph doesn't run by itself. You make a run from it, and the run calls the graph's nodes.

    Every example on the page uses the graph from conductor's README. lines splits a text into lines, shout is called once per line, and join collects what shout returned. Every output on the page is what the sample beside it prints.

    Back to the overview

    A run is outcomes.

    A run stores one outcome per call. A call is a node plus its item index in each loop. A call with no outcome hasn't been made, is still running, or failed.

    resume() and stream() run one scheduler.

    It is conductor's Scheduler. The stream adds a listener that turns what happens into events, and runs the scheduler on a thread of its own.

    A node's Policy says where it runs.

    A node is called on the scheduler's own thread unless its Policy sets concurrency above 1 or an attempt_timeout. Only an ExternalError, or a class in retry_on, is retried.

    A run you hold stays put.

    resume() works on a copy and returns it. Status and progress are worked out from what the run stores, each time you read them.

    Public what you import, write or read back

    Internal how conductor does it inside; you never import it, and it can change in any release

    Starting a run

    A run is made from a graph

    graph.with_inputs(...) checks the inputs and returns a run that hasn't started. Its status is ready. run.resume() calls every node that is ready, until the run is complete, waits for a person, fails or hits a limit. graph.run(...) is the two in one call.

    A sample and what it prints

    @registry.node("lines", title="Lines", description="...",
               policy=Policy(costs_nothing=True))
def lines(text: str) -> Series[str]:
    return text.splitlines()
# shout and join as in the README
graph = Graph.compile(make_graph(lines, shout, join), registry)

run = graph.with_inputs({"text": "a\nb\nc"})
print(run.status)
print(run.progress.nodes["shout"].model_dump())

counted = run.resume(only_costs_nothing=True)
print(counted.status, counted.progress.nodes["shout"].model_dump())

done = counted.resume()
print(done.status, done.outputs)
print(done.results)

    What the three calls show

    Before any call, shout's total is None. How many lines there are isn't known until lines returns.

    resume(only_costs_nothing=True) calls only the nodes whose Policy says costs_nothing. Here that's lines. Afterwards the run is still ready, and the host knows shout will be called three times, before anything costly runs.

    The next resume() doesn't call lines again, since its call has an outcome. It calls the rest.

    Inside resume()

    One pass of the scheduler Internal

    You write none of this. It decides the order your nodes are called in.

    The scheduler keeps a list of calls to try, ordered by each node's place in the graph. It takes the first, gathers its arguments, and makes the call if they are all there. Each outcome it stores puts the calls that read it on the list. A call that collects a loop, like join, is set aside instead, until no call upstream of it is running for the same item.

    The steps are a trace of the real scheduler, with {"text": "a\nb\nc"}. Switch shout's policy to see its calls on threads.

    What a call leaves behind

    Four kinds of outcome

    A call has at most one outcome, and once stored it doesn't change, except that an answer turns Unanswered into Done, and a decline removes every Unanswered. Three of the four kinds have outputs that the next node can read. Unanswered has none yet, so a call that reads it isn't ready.

    You never import the four classes. You see them through run.results, run.waiting, run.none_input_calls and run.status.

    DoneInternal

    The call has its outputs. The function returned them, or it asked and a person answered.

    UnansweredInternal

    The function raised Ask, and no answer has come. It keeps the prompt, the choices and the proposed answer.

    SkippedInternal

    The function wasn't called, because an input gets only SKIPPED. The node is downstream of a branch that wasn't chosen. Every output is SKIPPED.

    NoneInputInternal

    The function wasn't called, because an argument was None and its parameter doesn't take None. run.none_input_calls lists these.

    A sample and what it prints

    @registry.node("tidy", title="Tidy", description="...")
def tidy(line: str) -> str | None:        # None for a blank line
    return line.strip() or None

@dataclass(frozen=True)
class Gated:
    keep: str = SKIPPED                    # a branch
    drop: str = SKIPPED                    # a branch

@registry.node("gate", title="Gate", description="...")
def gate(line: str) -> Gated:              # "skip" goes to drop
    return (Gated(keep=SKIPPED, drop=line) if line == "skip"
            else Gated(keep=line, drop=SKIPPED))

@registry.node("approve", title="Approve", description="...", asks=True)
def approve(line: str) -> bool:
    if line == "ask":
        raise Ask(f"Approve {line}?")
    return True

graph = Graph.compile(make_graph(lines, tidy, gate, approve, edges=[
    ("lines.result", "tidy.line"), ("tidy.result", "gate.line"),
    ("gate.keep", "approve.line")]), registry)
run = graph.run({"text": "ok\n \nskip\nask"})
print(run.status, run.results["approve"]["result"])
print(run.results["gate"])
print(run.none_input_calls)
print([waiting.loc for waiting in run.waiting])

    How a run stands

    The status is read from the outcomes and the last resume Public

    run.status comes from the outcomes and from how the last resume() left the run. run.with_decline stores its own ending in the same place, declined, with answer_declined as its cause. The one rule, with the order its checks go in, is in the reference: python -m conductor.about running, under "The status".

    A sample and what it prints · the run above, waiting at approve

    print(run.status)
answered = run.with_answers(run.waiting[0], True)
print(answered.status)

declined = run.with_decline(run.waiting[0], reason="Over budget")
print(declined.status, declined.cause.type, declined.cause.loc)
print(declined.resume().status, declined.waiting)
    waiting
complete
declined answer_declined ('approve', 3)
declined []

    An answer is read from the outcomes at once: every call now has one, so the run is complete with no resume(). A decline drops every waiting question, and a declined run stays declined.

    Where and how often a call is made

    A node's Policy decides its thread, its limit and its retries

    A node with concurrency 1 or None and no attempt_timeout is called on the scheduler's own thread, one call at a time. Any other node is called on a pool of threads.

    Which failures are retried, how long each retry waits, and who counts the running calls are rules of the reference: python -m conductor.about retries-and-timeouts and python -m conductor.about versions-and-policies. The samples below show them at work. In each, chain(...) stands for Graph.compile(make_graph(...), registry) with a registry of those nodes.

    A sample and what it prints · the second value printed, policy.threaded Internal

    for policy in (Policy(), Policy(concurrency=4)):
    seen = set()

    @node("slow", title="Slow", description="...", policy=policy)
    def slow(line: str) -> str:
        seen.add(threading.current_thread().name)
        time.sleep(0.05)
        return line

    run = chain(lines, slow).run({"text": "\n".join("abcdefgh")})
    print(policy.concurrency, policy.threaded, run.status,
          "one thread" if len(seen) == 1 else "several threads",
          "main" if seen == {threading.main_thread().name} else "pool")
    None False complete one thread main
4 True complete several threads pool

    When a node raises

    A failure is a Problem, and the run stops starting calls Public

    The first call that fails, and isn't retried, ends the run as failed. Its problem is run.cause. The failed call stores nothing, so the next resume() makes it again. If the stream's cancel was set by then, the run ends cancelled instead. A call past its attempt_timeout still ends it failed, since the timeout isn't the cancel's doing. A node may stop a slow call by raising when it sees the cancel.

    A sample and what it prints

    @node("parse", title="Parse", description="Reads a number.")
def parse(line: str) -> int:
    return int(line)

@node("check", title="Check", description="Refuses a short line.")
def check(line: str) -> str:
    if len(line) < 3:
        raise NodeError("The line is too short.", code="too_short")
    return line

failed = make_and_run(lines, parse, {"text": "1\ntwo\n3"})
print(failed.status, failed.cause.model_dump(mode="json"))
print(failed.results["parse"]["result"])

refused = make_and_run(lines, check, {"text": "long\nno"})
print(refused.status, refused.cause.model_dump(mode="json"))
    failed {'type': 'execution_failed', 'loc': ['parse', 1], 'msg': "The node raised ValueError, which isn't retried: only an ExternalError, or a class in Policy(retry_on=), is. Its developer can find the details in the conductor log.", 'ctx': {'error': 'ValueError'}}
[1, None, None]
failed {'type': 'too_short', 'loc': ['check', 1], 'msg': 'The line is too short.', 'ctx': {}}

    make_and_run stands for Graph.compile(make_graph(...), registry).run(...).

    What reaches the host and what reaches the log

    The problem's loc names the call. It is the node's id, then its item indexes. Inside a subgraph, the subgraph node and its item come first.

    A NodeError is the node's own failure, written by its author. Its code and message are the problem, as too_short shows.

    Any other exception is written to the conductor logger with its traceback. The problem names only the exception's class, because its text may quote a value the run handled. It is external_failed for a class in the node's retry_on, and execution_failed for anything else.

    The third line of parse was never called. With parse's default policy its calls go in item order on one thread, and the failure of item 1 stopped the run before item 2.

    run.stream()

    run.stream() adds a listener to the same scheduler

    run.stream() is an async generator. It starts the scheduler on a thread of its own, so a slow node never blocks the host's event loop.

    Internal The listener, NodeEvents, turns what the scheduler reports about calls into events about nodes. An asyncio queue carries each event to the generator.

    A sample and what it prints

    async for event in graph.with_inputs({"text": "a\nb"}).stream():
        print(event.model_dump(mode="json"))

    Why the events come in that order

    lines completes only after join has started. The listener looks for complete nodes when no call is ready, and in this run that first happens after join is called. It's the last step of the walk above.

    node_progress comes at most four times a second for each node, plus one last count before the node's node_complete if the count changed. So finished=2 shows up only at the end.

    The events are the classes of conductor.events, in the order a run reports them. What each one carries, and when it comes, is in the reference: python -m conductor.about events. run_end and run_checkpoint also hand the host the run itself as event.run, which isn't part of the event's JSON.

    Limits and checkpoints

    A run can stop early and go on later Public

    Besides finishing, a run ends early when a call fails, a series goes over max_items, the stream is cancelled, or timeout passes. Each is a status with a cause. In each case no new call starts, and the calls on threads are waited for, each up to its attempt_timeout, and kept. A later resume() goes on from there, though a run stopped at the item limit needs a higher one first.

    A sample and what it prints

    # tick sleeps 30 ms, called once per line of ten
part = ticking.with_inputs({"text": ten_lines}).resume(timeout=0.1)
print(part.status, part.cause.type, part.progress.nodes["tick"].finished < 10)
rest = part.resume()
print(rest.status, rest.progress.nodes["tick"].finished)
    timed_out run_timed_out True
complete 10

    How many calls fit in 0.1 seconds depends on the machine. The timeout is checked before each call, so a call that has started finishes, and the next resume() makes only the rest.

    A sample and what it prints

    How many checkpoints come, and how far the last one is, depends on the machine. Whichever it is, the run read back goes on to the end.

    What a checkpoint is

    With checkpoint_every, the scheduler hands the host a copy of the run after an outcome is recorded, once at least that many seconds have passed since the stream started or since the last copy. One more copy comes when the run stops with calls still on threads, before those calls are back.

    Read back, a running copy's status is what its outcomes say. If the process dies, a resume of the last saved copy makes only the calls that copy has no outcome for.

    max_items, timeout and checkpoint_every are checked at the call, before anything runs. A wrong one is refused, and True isn't a number of seconds:

    for limits in ({"max_items": 0}, {"timeout": True}):
    try:
        ticking.run({"text": "a"}, **limits)
    except InvalidCallError as refused:
        print(limits, [problem.type for problem in refused.problems])
    {'max_items': 0} ['invalid_limit']
{'timeout': True} ['invalid_limit_seconds']

    Why it's built this way

    The design choices of this part

    Why nodes run on the scheduler's own thread unless they ask for threads, why concurrency counts across the whole process, why only failures from outside are retried, why one blueprint serves every run, and why events carry counts and checkpoints come from the stream: the design guide's engine section and its section on saved runs, checkpoints and events say. Why a node's own exception goes to the log is under Graph and Run. The choices below are the rest.

    One scheduler runs a run, with or without a listener.

    What a test sees with resume() is how a served run calls its nodes.

    An attempt past its timeout fails the call without a retry.Public

    Python can't stop a thread, so the old attempt may still be doing its work, and a retry could do the work twice. A later resume() still makes the call again, and with concurrency unset it can run beside the old thread.

    Cost: the call keeps its place under concurrency until its function returns.

    A failed call stores nothing, and the first failure ends the run.Public

    The run has one clear cause, and resume() makes the failed call again.

    Cost: one bad item stops the items after it. On one thread, a later item isn't started.

    Status and progress are worked out when read.Public

    There's no counter to keep in step, and a run read back with Run.from_json in another process has the same status and progress. The exception is a copy made while the run goes on, which reads back as its outcomes say.

    Cost: reading run.progress looks at every outcome each time.

    A run you hold doesn't change.Public

    resume(), again() and each with_... method (with_answers, with_decline, with_inputs, with_forgotten, with_max_items) return a new Run. A host can keep the run it started from, and a checkpoint's copy is safe to save while the scheduler goes on. Setting an attribute of a Run raises FrozenInstanceError.

    Cost: each resume() copies the run's outcome dicts, one per node.
