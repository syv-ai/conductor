    Serving runs

    Some runs outlive a request. A node asks a person to approve something and the answer comes tomorrow, or the server is deployed halfway through a long run. syv-conductor-providers keeps such runs in your database and serves them over HTTP, from one server process or ten.

    It is a separate package, imported as conductor_providers. Everything in it is under conductor_providers.fastapi. You write a store, build a Worker on it, and mount run_router in front of the worker.

    The overview Asking a person Running and streaming Saved runs and reuse Problems

    A store you write.

    Its async methods act on one row per run. Every change to a row is a compare-and-set on its rev.

    class RunStore(Protocol):
    async def create(self, run)
    async def get(self, run_id)
    async def update(self, run_id, rev, changes, event=None)
    async def expired(self, now)
    async def add_event(self, run_id, owner, body)
    async def events(self, run_id, after)

    A worker that holds leases.

    It starts, answers, declines, resumes and cancels runs. While it resumes a run it holds a lease on it, and another worker takes the run over if the lease runs out.

    Each route but /compile reads its request, calls the worker, and answers with what it returned.

    Here is a store kept in a dict, which every sample below runs on, and check_run_store run on it and on a store that gets update wrong. What a store must do is written once, in Serving runs over HTTP and in python -m conductor.about serving-runs (its part "The store").

    store.py, the dict store the samples below use

    class DictStore:
    def __init__(self, log=None):
        self.rows, self.bodies, self.log = {}, {}, log

    async def create(self, run: StoredRun) -> None:
        self.rows[run.id], self.bodies[run.id] = run, []

    async def get(self, run_id):
        return self.rows.get(run_id)

    async def update(self, run_id, rev, changes: RunChanges, event=None) -> bool:
        row = self.rows.get(run_id)
        if row is None or row.rev != rev:
            if self.log is not None:
                self.log(run_id, rev, changes, False)
            return False
        self.rows[run_id] = dataclasses.replace(row, **changes, rev=rev + 1)
        if event is not None:
            self.bodies[run_id].append(event)
        if self.log is not None:
            self.log(run_id, rev, changes, True)
        return True

    async def expired(self, now):
        return [r for r in self.rows.values()
                if r.lease_until is not None and r.lease_until < now]

    async def add_event(self, run_id, owner, body):
        if self.rows[run_id].owner != owner:
            return False
        self.bodies[run_id].append(body)
        return True

    async def events(self, run_id, after):
        return [(n, b) for n, b in enumerate(self.bodies[run_id]) if n > after]

    class ForgetsTheRev(DictStore):
    async def update(self, run_id, rev, changes, event=None):
        row = self.rows[run_id]
        self.rows[run_id] = dataclasses.replace(row, **changes, rev=row.rev + 1)
        return True

async def until_stopped(worker, run_id):
    while (view := await worker.read(run_id, allows=lambda m: True)).status == "running":
        await asyncio.sleep(0.01)
    return view

async def main():
    store = DictStore()
    worker = Worker(store, nodes_for=lambda metadata: registry)
    async with worker.serving():
        view = await worker.create(make_graph(approve), {"amount": 5000}, {"user": "anna"},
                                  allows=lambda m: True)
        print("create ->", view.status, view.waiting)
        print("compiles after create:", compiles)
        view = await worker.resume(view.id, allows=lambda m: True)
        view = await until_stopped(worker, view.id)
        print("read   ->", view.status, [w.id for w in view.waiting], view.waiting[0].prompt)
        print("compiles after the first resume call:", compiles)
        row = store.rows[view.id]
        print("row.state =", dumps(json.loads(row.state)))
        print("row.owner =", row.owner, " row.lease_until =", row.lease_until)
        answered = await worker.answer(view.id, {view.waiting[0].id: True}, allows=lambda m: True)
        print("answer ->", answered.status)
        view = await until_stopped(worker, view.id)
        print("read   ->", view.status, view.outputs)
        print("compiles after answer and second resume call:", compiles)
        print("events:")
        async for n, body in await worker.events(view.id, allows=lambda m: True):
            print(" ", n, json.loads(body)["type"], json.loads(body).get("status", ""))

    worker.py, held_run.py

    Every load compiles the graph again

    No worker keeps a compiled graph or a Run in memory between calls. Each time it needs the run, it builds it from the row with Run.from_json(row.run, Graph.compile(row.graph, nodes)). So any worker can pick up any run. Saved runs and reuse explains to_json and from_json.

    Sample 1 counts the compiles as it goes: create compiles the new graph once, each resume call compiles it again, and the answer to a waiting run loads it once more to give it the answers. read loads nothing, since it answers from the row. Which of the worker's other calls load a run, such as again or begin(previous=), each method's docstring in worker.py says.

    The one rule

    Every update is at the rev the writer read

    update(run_id, rev, changes) writes only while the row is still at rev, and moves it on by one. Of two writes made from the same read, the second loses. Its writer reads the row again and acts on the run as it is then, except a sweep, which leaves the run to the winner. Your store's part of this is update. Reading the row again is the worker's.

    Sample 3, race.py, where both workers answer at once and the store logs each claim and each write of state · the queued lines Internal

    Each answer loads the run on a thread before it claims, so either worker can win, even on one event loop. Both give the same answer here, so the outcome is the same whichever wins: one claim written, one resume call, and one answer queued and refused. check_run_store sends updates at one rev at once, several times over, and fails a store that lets more than one through.

    store = DictStore()
one = Worker(store, nodes_for=lambda metadata: registry)
other = Worker(store, nodes_for=lambda metadata: registry)

async def race():
    async with one.serving(), other.serving():
        view = await one.create(make_graph(approve), {"amount": 5000}, {"user": "anna"}, allows=every)
        await one.resume(view.id, allows=every)
        waiting_id = (view := await until_stopped(one, view.id)).waiting[0].id
        store.log = log  # from here on, the store prints what it is asked to write
        a, b = await asyncio.gather(
            one.answer(view.id, {waiting_id: True}, allows=every),
            other.answer(view.id, {waiting_id: True}, allows=every),
        )
        store.log = None
        print("both answered:", a.status, b.status)
        view = await until_stopped(one, view.id)
        print("ended:", view.status, view.outputs)
        print("refused:", {k: [p.type for p in v] for k, v in view.refused.items()})

    Many workers share one store

    A lease passes between two workers

    While a worker resumes a run, it is the row's owner and keeps moving lease_until on. Every serving worker sweeps the store three times a lease for rows whose lease_until is past, and claims each at the rev it read. Pick what happens to worker A.

    The leases and the sweep are internal. You set their pace with the Worker's lease= (30 seconds by default), and how often a running run is saved with checkpoint_every= (5 seconds). What a host sees is a run that goes on after its worker shuts down or dies.

    Sample 2, hand_back.py. Worker A creates and resumes a run of 40 slow items and shuts down after 10 calls. Worker B serves after it. The store prints each update that writes owner.

    Answer, decline, cancel, resume

    What a call does depends on where the run is

    Each method that acts on a run reads its row, acts on it as it is, and returns the run as written. A running run queues an answer or a decline in its row's state, as sample 3 shows, and is given the queue when its resume call ends. A run that isn't running takes a reply at once: sample 4 declines a waiting run and gets it back declined, for good.

    The rules for each call on a run in each state are written once. python -m conductor.about answers-and-declines has the queue's, and python -m conductor.about serving-runs has a cancel's and a resume's (its parts "Cancelling" and "Refusals"). Serving runs over HTTP walks through them. The engine's side is in asking a person and running and streaming.

    Metadata and the run filter

    Who started a run and who may see it Public

    Every run keeps the metadata the router's metadata dependency gave when it started, such as who started it. Each time any worker resumes the run, it builds the run's registry (nodes_for) and context (context) from that metadata. run_filter gives, per request, a test of a run's metadata, which the router passes to the worker as allows=. A run it turns away is a 404, as one that isn't there: sample 4's GET as bo.

    The rules are in Serving runs over HTTP and in python -m conductor.about serving-runs (its parts "Metadata" and "Access").

    In the typed form, everyone in a team sees the team's runs. The model and the two dependencies are from docs/serving-runs.md.

    class Member(BaseModel):
    user: str
    team: str

def current_member() -> Member:
    return Member(user="anna", team="sales")  # yours: your login

def team_runs(member: Annotated[Member, Depends(current_member)]) -> Callable[[Member], bool]:
    return lambda started: started.team == member.team

worker = Worker(DictStore(), metadata_type=Member, nodes_for=lambda member: registry)
app = FastAPI()
app.include_router(run_router(worker, metadata=current_member, run_filter=team_runs))

    A RunView's metadata is the JSON object the row keeps, whatever M is, so the view is one OpenAPI component. tests/test_providers/typed_setups.py has mypy hold nodes_for and context to M and to the registry's context type.

    Why it's built this way

    Design choices

    Why the host writes the store, and what it costs, is in the design guide. Why every change is a compare-and-set on rev, and how a kill, a deploy, a store outage and two answers at once play out, is in Serving runs over HTTP, which also says why a run you may not see answers as one that isn't there and why replies to a running run are queued. The choices below are the ones this page shows.

    The worker keeps no run in memory between calls.

    The registry and context are built again from the run's metadata on every resume, on whichever worker that is, and the graph is compiled from the row. So any worker can serve any request.

    Cost: a compile per load, which sample 1 counts.

    The state column stays small, and outcome may be large.

    An answer, a decline or a cancel sent to a running run writes only state and status. state stays small however large the run is. outcome can be megabytes, so it is written when the run stops and with each checkpoint.

    Cost: the read before that write still fetches the whole row, run and outcome included.

    A body with a graph is read once, as text.

    POST /runs, /estimate and /compile read their body with conductor's read_json, so a key written twice, such as two nodes with one id, is a 422 invalid_record rather than a node quietly dropped.

    Cost: FastAPI doesn't parse these bodies, so it can't derive their schema. bodies.py's declared() builds it from the model and inlines every $ref, and it goes in through openapi_extra. Your OpenAPI page shows the schema all the same.
