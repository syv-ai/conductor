    How conductor says what went wrong

    Whatever is wrong with a graph, a call, a run or a declaration, conductor reports it as one kind of model, a Problem. So a host has one thing to show, to store and to translate.

    Here is a real one. Compiling a graph that wires a node returning an int into an input that takes a str lists this problem in graph.problems:

    type"type_mismatch"It is the code. It stays the same between versions, so a host translates by it.
    loc("u", "text")It says where the problem is. Here it is the node u and its input text.
    msg"'c.result' gives int, but 'u.text' takes str. Wire an output that gives str, or convert the value in a node in between."It is the message for a person, in English. Most say what is wrong, then how to fix it. Show it, but don't parse it.
    ctx{ "node_id": "u", "input": "text", "source": "c.result", "got": "int", "expected": "str" }They are the values the message was made from, by name. A host can write its own message from them.

    They are the four fields of a pydantic error, so a Python developer has seen the shape before. Problem is a frozen pydantic model, so it goes to and from JSON as it is.

    When a problem is found

    A problem reaches you at one of four moments Public

    A problem is found when the module that declares a node is imported, when a graph is compiled, when a call is made on it, or while it runs. Each moment reports in the way that suits whoever has to act on it.

    What a declaration checks is on the node and types page, and what compiling checks on the graph and compiling page. This page is about how either one tells you.

    How a kind of problem is declared

    A kind of problem is a small function Public

    Each kind of problem, such as unknown_input, is a plain function under @catalogue.problem. The catalogue is a ProblemCatalogue. The function's parameters are the loc and the ctx. It returns the message. Calling it makes the Problem. A package that reports problems of its own declares them the same way, as conductor-providers does.

    Pick a rule to see where each part of the signature goes.

    Each mistake has a code of its own

    Some mistakes are common enough to deserve a message of their own. Each is a kind of its own, with its own code. Kinds that belong together share the start of their code, and the end names the cause. A second kind with a code the catalogue already has is refused with a TypeError where it is declared, so the module that declares it fails to import.

    Conductor's own type_mismatch works this way. It is for any two types that don't meet. type_mismatch_whole_table_or_list is for a whole table or list wired into an input that takes one value, type_mismatch_missing_column for a table that lacks a column the input needs, type_mismatch_series_given_one_value for a Series input wired to one value per call, and type_mismatch_series_into_list for a Series wired into a list[T] input that should be declared Series[T]. The catalogue below has all five.

    @SHELF.problem
def unknown_shelf_in_another_room(room: str, shelf: str, /, *, other: str) -> str:
    return f"'{shelf}' is a shelf of '{other}', not of '{room}'."

    A host that writes its own messages

    The message is in English. A host that shows another language looks up the kind by type, and fills its own sentence from ctx. The kind's sentence is the English template, with a slot for each ctx value.

kinds = {kind.code: kind for kind in PROBLEMS}
kind = kinds[problem.type]
print(kind.section)
print(kind.sentence)

    Where the kinds live

    The kinds are kept in catalogues

    A ProblemCatalogue lists its kinds in the order they were declared. Conductor's public catalogues are PROBLEMS and DECLARATION_PROBLEMS in conductor, and REGISTRY_CHECK_PROBLEMS in conductor.testing.

    Inside, conductor's core has one module for each section of the problems page, each with its own catalogue. Code that reports a problem imports the module and calls the kind, like compile_problems.cycle(node_id).

    A test keeps a host's translations complete Public

    PROBLEMS.codes is every code conductor's core reports for a graph, a call or a run. Any other code there is a node's own, from NodeError(code=...), or a companion's, like the worker's raised_outside_a_node. The reference suggests a test that keeps a host's translations complete when conductor adds a code. It asks for a translation of every code in PROBLEMS, and lets a host also translate the declaration and check_registry codes.

    def test_translations_match_the_codes(translations: dict[str, str], own_codes: set[str]) -> None:
    assert PROBLEMS.codes <= translations.keys()  # every code conductor writes is translated
    known = PROBLEMS.codes | DECLARATION_PROBLEMS.codes | REGISTRY_CHECK_PROBLEMS.codes
    assert translations.keys() - own_codes <= known  # every other translation names a real code
    print(len(PROBLEMS.codes), "unreadable" in PROBLEMS.codes, "type_mismatch" in PROBLEMS.codes)

    When a node fails

    What a node raises decides its problem Public

    Conductor sorts what a node's function raises into a few cases. The case decides whether the call is tried again, which code the problem gets and what a person is told. Pick what the node raised.

    Two classes a node raises

    NodeError(message, code=..., ctx=...) is a node's own failure, with a message written for people. It carries one problem, made when it is raised, with an empty loc. Conductor fills in the call's loc. Without a code, the code is node_error. The ctx takes JSON values only. A set, say, raises pydantic's ValidationError from the node's own raise, and the call fails with execution_failed, naming ValidationError.

    ExternalError is a NodeError for a failure of the outside world, such as a network error, a rate limit or a server error. It is retried as the node's Policy says. Retry n waits retry_delay * 2 ** (n - 1) seconds, so with retry_delay=0.01 the waits above are 0.01 and 0.02. A call that runs past its attempt_timeout fails with timeout and isn't retried. The events are on the running and streaming page.

    The problems page

    The problems page is written from the code

    python -m conductor.about problems prints every code with its message, an example that makes it, what its ctx keys mean and how to fix it.

    The examples use four helpers from the page's setup, one for each moment. declaration_refused(lambda: ...) catches a NodeDeclarationError, problems(record) compiles a graph record, refused(lambda: ...) catches an InvalidCallError, and why_it_stopped(run) returns run.cause. In the four core sections, an example's last line calls its section's helper, so the problem turns up where the section's text says a host finds it.

    One entry prints on its own by its slug. The slug is the code with hyphens.

    check_registry tests a whole registry Public
    
  
    
  
    
    
    
      
    @node checks a node when it is declared. Some faults only show when the node is used, such as a hook that fails on the node's defaults, an older version that doesn't upgrade cleanly, or a node that changes a list it was given. check_registry looks for these and returns every problem it finds, so a node package or a host adds one test to its suite.
    
      
    Its problems are Problems too, with a loc of (node_id, version). An example keyed by an id alone that isn't in the registry has (node_id,), as here. A node's function is called only for a node given an example, since a node might send mail or charge a card. Each example runs through the engine, as a graph of that one node. A check that fails because of a problem conductor reports, like example_run_failed, gives one problem for each problem behind it, with that problem's message in ctx.reason, its code in ctx.problem and its loc in ctx.loc.

    Why it's built this way
    
    
    Ten design choices
    
    
    The one marked Internal changes nothing in your code.
    
  
    
  
    
    
    
      
    One model says what is wrong.
    
      
    A graph's problem, a refused call, a run's cause, a node's failure, a declaration fault and a check_registry finding are all a Problem. A host learns one shape, and translates one way.
    
      
    The cost is that a Problem read from JSON isn't typed by its code. A host that wants ctx typed validates it against the kind's ctx_type itself.
    
    
    
    
    
      
    A kind of problem is a plain function.
    
      
    A type checker checks each call against the signature. The code, the template sentence and the ctx keys are all worked out from that one signature, so they can't drift apart.
    
      
    The cost is that the signature has rules. A loc part is positional-only, a ctx key is keyword-only, and no default but None is allowed. A function that breaks one is refused with a TypeError where it is declared.
    
    
    
    
    
      
    A part of loc is given by position only.
    
      
    Then it lands in loc and in ctx at once, so the two agree, and a host fills a sentence from ctx alone without reading loc.
    
    
    
    
    
      
    Each mistake a host may tell apart has its own code.
    
      
    A host translates by type alone, so one lookup finds the message for every problem. Kinds that belong together share the start of their code, and the end names the cause, never the fix.
    
      
    The cost is more codes to translate: PROBLEMS.codes has 77.
    
    
    
    
    
      
    Each moment reports in its own way.
    
      
    A graph's faults are data, so an editor shows them while the graph is drawn. A refused call raises with every fault it found in what it checked, before anything changes. A run that stops keeps its cause, so it can be saved and resumed.
    
    
    
    
    
      
    A declaration fault raises where it is declared.
    
      
    That is usually at import. The fault is in code, so it fails where the developer will see it. It is also a TypeError, as InvalidCallError is pydantic's ValidationError and so a ValueError, so an except a developer already writes still catches it.
    
    
    
    
    
      
    A problem never quotes a value a graph carries.
    
      
    A host may send problems to a browser, and a value can be private. So a problem never quotes a graph input or its default, a constant, an output, an answer or a value in a saved run. A fault inside such a value is placed by list indexes and declared fields, never by the value's own dict keys. A refused value says why in ctx.errors, one error per fault, each with a stable type a host translates by, and none quoting the value. Its pydantic errors lose the value with value_free_errors.
    
      
    A problem never quotes the text of an exception other than a NodeError, since it might quote a value. The text and its traceback go to the conductor logger, and ctx.error has the class name. That holds for a node, a hook (compute_hook_raised), an input a question can't write as JSON (question_unwritable) and an Upgrade's rewrite (cannot_move_to_version_raised).
    
      
    A problem may name what a developer or a host wrote: ids, input, output and field names (a hook's too), places, waiting ids, a type's limits, a host's decline reason and where a JSON text stops being JSON, which is the position text invalid_record gives for text that isn't JSON. A NodeError keeps its message and its ctx, since its developer wrote them for people.
    
      
    The cost is that the details of an exception are in the log, not in the problem.
    
    
    
    
    
      
    Only what the node marks as the outside world's is retried.
    
      
    That is an ExternalError, or a class the node names in retry_on. A network error or a rate limit may pass on the next try, which a bug or bad data won't. A NodeError other than an ExternalError, a refused output and an Ask never are.
    
      
    The cost is that conductor can't tell. A class named in retry_on is retried and reported as external_failed, even a bug's.
    
    
    
    
    
      
    The problems page is written from the code. Internal
    
      
    Each kind's docstring is its entry, and a test runs its example and checks the problem it makes. So the page can't keep a code that is gone, or an example that makes something else.
    
      
    The cost is that a kind's docstring has a fixed form. It has its text, an Args line for each ctx key, an optional one for loc, and an Example. In the four core sections, the example's last line calls the section's helper.
    
    
    
    
    
      
    check_registry's codes stay out of PROBLEMS.
    
      
    A host never meets them from a graph or a run, so its translation test, built on PROBLEMS.codes, doesn't ask it to translate them.
