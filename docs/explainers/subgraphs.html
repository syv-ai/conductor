    A graph inside a graph

    A subgraph is a graph record used as one node of another graph. You make it with subgraph(...), much as you make a node from a function with @node (see a node and its types). The graph that uses it is the outer graph, and the nodes in its record are its inner nodes.

    Back to the overviewPR #106, the core

    Outside, it's one node.

    Its record is compiled on its own.

    A run calls the nodes inside, never the subgraph node.

    Publicwhat you import, write or read back

    Internalhow conductor does it inside; you never import it, and it can change in any release

    The model

    Three views of one subgraph

    loud is the subgraph strip → shout. The outer graph splits a text into lines, runs loud's nodes once per line, and joins the results. The first view is what you wire. The other two are how conductor compiles and runs it. Every output on this page was printed by the code at 7d2df580, on Python 3.12.11.

    Compiling

    How a subgraph node is compiled

    When a graph is compiled, each subgraph node's record is compiled on its own first. A problem inside comes back with the subgraph node's id in front of its loc. The node is left out, so describe() says it wasn't found. A subgraph that contains itself, at any depth, is subgraph_contains_itself. Otherwise the node's inputs and outputs are the inner graph's. Each output keeps the field of the inner node that returns it, under the graph output's name.

    What _compile_subgraph_node does Internal

    1. Refuse a subgraph that contains itself

      Each compiler knows the ids of the subgraphs it's inside (inside_subgraphs). If the subgraph's id is among them, the node gets subgraph_contains_itself.

    2. Compile its record with a Compiler of its own

      A new Compiler gets the same registry and the longer stack of subgraph ids. All the compilers of one Graph.compile call share one dict of compiled subgraphs (compiled_subgraphs), keyed by id, version and that stack. So a subgraph used twice, inside the same subgraphs, is compiled once in that call.

    Places and ids

    How a place inside a subgraph is written Public

    Problems, events, waiting calls and saved runs all say where something happened. There are four ways to write it. Each is a tuple for code and a text for people. The texts use ., /, @ and ~ as separators, so no node id and no input or output name may contain any of them.

    Node pathloud/shout

    A node's id, after the id of each subgraph node it's inside. A run stores a node's outcomes under it.

    Item indexes(1,)

    Which call of a node. There is one index per loop the node is inside, outermost first.

    Locloud@1/shout

    It names one call. Each index goes right after the node that's inside its loop, in the graph where the loop is. As a tuple: ("loud", 1, "shout").

    Sourceloud.result

    Where an edge reads from. It is an output of a node in the same graph, maybe one field of it. It is never a node inside a subgraph.

    Every call of one run

    The outer graph is lines → review, where review is the subgraph strip → check. strip gives None for a blank line, and check asks a person. The run got the text "a\n \nc". Pick a call to see how each part of conductor names it.

    Every waiting id, loc, outcome and prompt is printed by the run at 7d2df580, on Python 3.12.11. The hex after ~ is the same on any Python version, since the node's code goes into it as its parsed source. The node paths and saved positions are worked out from them.

    The sample

    review = subgraph("review", title="Review",
    description="Trims a line and asks a person about it.")(
    make_graph(strip, check, edges=[("strip.result", "check.line")])
)
registry.add(review)
graph = Graph.compile(make_graph(lines, review,
    edges=[("lines.result", "review.line")]), registry)

run = graph.run({"text": "a\n \nc"})
for w in run.waiting:
    print(w.id, w.loc, w.prompt)
for n in run.none_input_calls:
    print("none input:", n.loc, n.input)
run2 = (run.answer("review@0/check", True)
           .answer(run.waiting[1].id, False).resume())
print(run2.status, run2.outputs)

    What it prints

    An answer may name the call without the part after ~, as the first answer in the sample does with "review@0/check". With it, the id also carries a fingerprint of the node, the call's inputs and its items, and an answer to an id whose fingerprint no longer matches is refused (answer_stale).

    Loops

    A subgraph that loops inside

    A node outside reads a subgraph's output as it would read the same node drawn in its own graph. Take per-line, the subgraph documents → lines → upper. lines runs once per document and upper once per line (how loops work is on Series and tables), so the output result is a list of lines for each document.

    g = Graph.compile(make_graph(per_line, join,
    edges=[("per-line.result", "join.texts")]), registry)
run = g.run({"text": "a,b;c"})
print(run.results["per-line"]["result"], run.results["join"]["result"])
print(g.describe().nodes["join"].per_item_of)
out = g.describe().nodes["per-line"].outputs[0]

    An output's description keeps the type of one value, str, and lists its loops outermost first. Each entry is one level of list.

    Internal Compiling asks the compiled subgraph node's inner graph for each output's loops, the node that returns it and the branches it needs.

    Two outputs from loops that don't nest can't be paired. When one of them is made inside a subgraph, no edge in the outer graph can fix that, and the problem says so.

    The sample prints the problem's type and loc, then series and subgraphs from its ctx, then its message. Line breaks are added here.

    In the palette

    A registry describes a subgraph by compiling it

    A subgraph's inputs and outputs depend on the nodes its record uses, and those are in the registry. So SubgraphDefinition has no describe() of its own. registry.describe() compiles a one-node graph that uses the subgraph and reads that node's inputs and outputs. It keeps the result until the registry's nodes change. A subgraph whose own graph has problems on the registry's nodes, such as a node the registry doesn't have yet, is left out of registry.describe(), with one warning on the conductor logger.

    registry.add(
    subgraph("shout-names", ...)(make_graph(each, upper,
        edges=[("each.result.name", "upper.text")])),
    subgraph("shout-contacts", ...)(make_graph(known, each, upper,
        edges=[("known.result", "each.value"),
               ("each.result.name", "upper.text")])),
)
palette = {d.id: d for d in registry.describe().nodes}
print(palette["shout-names"].inputs[0].type)
print(palette["shout-contacts"].inputs[0].type)
registry["shout-names"].describe()
    Table | list
Table[name: str]
AttributeError: 'SubgraphDefinition' object has no attribute 'describe'

    The example is from docs/subgraphs.md, which is in #109, the docs. each is generic: def each[T](value: Table[T] | list[T]) -> Series[T].

    A subgraph is compiled with nothing wired into it. A type variable at one of its graph inputs has no edge to bind it, so shout-names offers Table | list, and its edge each.result.name can't be checked until a run. shout-contacts starts with known, whose input says exactly what it takes, so the subgraph offers Table[name: str] and its edges are checked when it's compiled.

    The palette entry also says asks when any node inside asks, at any depth. For review above, registry.describe() gives the input line, the output result and asks true. takes_added_inputs and computes_outputs are false for every subgraph.

    Why it's built this way

    Seven design choices

    A subgraph is made like any node definition.Public

    subgraph() takes @node's arguments, less policy, the hooks and asks. So a registry, a graph record and registry.upgrade treat it as any node. It has an id, versions and a palette entry.

    Cost: it has no Policy, so a whole subgraph can't be retried or limited as one unit. Each inner node uses its own.

    Its interface is its record's graph inputs and outputs.Public

    An edge reads loud.result, an output of a node in its own graph. No name may contain /, so no edge can reach a node inside. What the subgraph offers is what its record declares, and nothing else.

    The same Compiler compiles it on its own.Internal

    One set of rules covers every graph. So a subgraph's faults are the same problems as anywhere, with the subgraph node's id in front of their loc. You see the choice in a problem's loc, and in the loose input type the palette offers, which is its cost.

    Cost: nothing wired in is known when it's compiled. A generic first node gives the subgraph a loose input type, like Table | list.

    A run calls only function nodes, from a flat blueprint.Internal

    When a graph's first run is made or read, RunBlueprint.of lists every function node of the graph and its subgraphs by full path. So a node inside gets one call per item of every loop it's inside, its own Policy, and its own reuse. A Series input inside still collects only the loops inside the subgraph.

    Cost: the subgraph node has no outcomes of its own. Its results, progress and events are worked out from the nodes inside it.

    A loop inside is named by the list inside.Public

    The loop over documents.result inside per-line is per-line/documents.result. Two outputs returned in that loop name the same loop, so they line up item by item outside.

    Cost: outputs from two loops inside that don't nest can't be paired by any edge outside. The problem says to change the subgraph or collect one of them.

    A call has one address wherever it is named.Public

    A loc puts each item index right after the node inside its loop: ("review", 0, "check"). Problems, waiting calls and run.none_input_calls use it, and a waiting id writes the same thing as text, review@0/check.

    The palette entry comes from the registry, not the definition.Public

    Its fields depend on the nodes the record uses, so the registry compiles it to find them. A definition with its own describe() couldn't know them without a registry.

    Cost: registry.describe() compiles each subgraph's entry once, with every subgraph inside it, and again on the first registry.describe() after the registry's nodes change. Each Graph.compile compiles its subgraphs afresh.
